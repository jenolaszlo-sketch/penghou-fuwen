# Fuwen product, design, and implementation review

Date: 2026-09-20

Reviewed checkout: `4c63a8b` (`0.1.0-preview.10`)

Scope: compiler, core contracts, Zhinu and Baize adapters, tests, authoring experience, documentation, and release workflows.

This is a new review, not a replacement for the historical [implementation review](../review.md). No implementation changes were made. Findings R31 onward extend that document's numbering; recommendations below are proposals, not shipped features. Source line numbers refer to the reviewed commit. Implementation progress is tracked in the [remediation and product-evolution plan](review-remediation-plan-2026-09-20.md).

## Executive assessment

Fuwen has a genuinely strong foundation: it makes AI workflows into inspectable, typed, versioned executable plans, with an explicit admission boundary and durable evidence. The separation between describing work, authorizing work, and executing work is worth protecting.

Its best opportunity is to make **changing an AI workflow safely** a compelling everyday experience: inspect a generated plan, understand its tools and context, approve it, run it, diagnose a failure, change one part, and explain which previous results can be reused. That is a more distinctive product story than another way to sequence model calls.

The main obstacle is completeness across boundaries. Individually tested language features do not always survive the whole path from source to provider request. The current suite is green, but this review reproduced a tool-allowlist mismatch, an unexecutable registered-prompt alias, misleading revision explanations, ignored media timeouts, dropped context, and broken catalogue shorthand. The machine-readable authoring grammar also loses its newer inference production when read by a common JSON consumer.

My recommendation: make the next milestone a **trustworthy, easy-to-try vertical slice**, not another expansion of the language. Fix the defects below, then ship a credential-free reference application demonstrating the complete edit/review/run/recover loop.

## What should stay

- **The authority boundary.** Source requests capabilities; trusted host policy grants them. Identity and revision lineage are not authorization. The in-process nature of admission receipts is explicitly documented.
- **Immutable, exact identities.** Canonical fingerprints, descriptor digests, artifact references, and stable node paths create a useful basis for audit and replay. Improve their authoring ergonomics without weakening them.
- **The package boundaries.** Fuwen should remain the language/compiler/contracts layer; Zhinu the durable execution layer; Baize the inference integration layer. Product-specific workflows belong in consumers such as Guyabano.
- **Bounded semantics.** Bounded loops, fan-out, typed outputs, and constrained bindings are strengths. A general-purpose scripting escape hatch would undermine the main value proposition.
- **Recovery-oriented testing.** SQLite-backed recovery and evidence tests, canonical golden vectors, and multi-target verification are valuable assets. Extend them across new feature combinations.

## Findings to address before expanding the surface

P1 means an important declared safety boundary is violated in a supported configuration. P2 means a reproducible functional, usability, or release-integrity defect. These priorities are review judgments, not vulnerability severity scores.

### R31 — P1: Registered-template inference exposes tools outside the declared allowlist

**Status:** resolved in the working tree as of 2026-09-20. The
registered-template provider request honors the explicit v8 set, Zhinu
preserves `tools none` as an empty execution-port collection, and evidence
records the effective model-visible descriptors. Regression tests cover
none/subset/full/missing, historical defaults, repeat and fan-out paths,
persisted recovery, replay, and repeat-step restart on .NET 8 and .NET 10.

**Evidence:** [BaizeInferenceExecutor.cs](../src/Penghou.Fuwen.Baize/BaizeInferenceExecutor.cs), lines 354–366, 539–570, and 875; [FuwenZhinuSequentialInterpreter.cs](../src/Penghou.Fuwen.Zhinu/FuwenZhinuSequentialInterpreter.cs), lines 234–248.

Workflow-owned prompts use `SelectDeclaredTools`. The registered-template branch instead sends every tool in `binding.Tools`. The preliminary check only verifies that requested tools exist; it does not remove unrequested tools. Evidence records `request.Tools`, so the recorded set can differ from the model-visible set.

**Reproduced:** a v8 source workflow declaring only `search` compiled and passed admission. Executing the corresponding request against a host binding containing `search` and `write` sent both definitions to the fake model while recording only `search`. The request succeeded.

This proves an allowlist/evidence mismatch, not that a real write was executed. Nevertheless, exposing undeclared host tools violates the advertised inference boundary and matters especially when hosts supply tool-executing clients.

**Recommended fix:** apply the explicit v8 allowlist in both prompt modes. Preserve historical v3–v7 semantics through an explicit versioned contract, not an ambiguous null/empty convention. The Zhinu template path currently collapses an empty tool list to null, which also needs attention for `tools none`.

**Acceptance tests:** real source-to-Zhinu-to-captured-provider tests for none, subset, missing binding, and full set; both prompt modes; v8 and historical compatibility. Assert that model-visible tools and recorded admitted tools match exactly.

### R32 — P2: Registered prompt aliases compile and admit but cannot reach execution

**Evidence:** [FuwenSourcePromptTests.cs](../tests/Penghou.Fuwen.Compiler.Tests/FuwenSourcePromptTests.cs), line 312; [Prompts.cs](../src/Penghou.Fuwen/Prompts.cs), lines 138–145 and 202–231; [FuwenZhinuSequentialInterpreter.cs](../src/Penghou.Fuwen.Zhinu/FuwenZhinuSequentialInterpreter.cs), lines 250–281; [ExecutionPorts.cs](../src/Penghou.Fuwen/ExecutionPorts.cs), lines 151–156.

The supported declaration `prompt greeting(name: string) uses registered "...";` intentionally has no inline messages. Zhinu nevertheless runs it through `PromptRenderer`, which renders those zero messages. Constructing the resulting workflow-owned inference request rejects an empty rendered prompt. No registered-source resolution branch exists on this path.

**Reproduced:** compilation succeeded, admission succeeded, rendering returned zero messages, and the same request construction used by the interpreter threw `A workflow-owned prompt request requires rendered messages.` This probe exercised the component seam; the complete Zhinu scheduling path was traced in source rather than separately executed.

**Recommended fix:** implement an explicit host-bound registered-prompt resolution/mapping path with exact source identity and typed parameter validation. If execution support is deferred, reject this shape during adapter preflight with a source-located diagnostic, rather than accepting it until a run fails.

**Acceptance tests:** execute an alias through Zhinu and a fake Baize provider; verify parameter mapping and registered identity. Cover missing bindings, changed descriptors, and failure before any provider invocation.

### R33 — P2: Prompt-binding changes are reported as unchanged nodes

**Status:** resolved in the working tree as of 2026-09-21.
Canonical prompt-binding values are compared as node dependencies, reordered
bindings remain equivalent, and changes to a named prompt's definition are
attributed to referencing inference nodes while retaining the root semantic
change. Fixtures cover literals, input projections, node-source retargeting,
canonical binding order, and downstream explanatory behavior.

**Evidence:** [PlanRevisionComparer.cs](../src/Penghou.Fuwen/PlanRevisionComparer.cs), lines 177–215.

Inference node semantics include only prompt parameter names. Its dependency comparison includes arguments and contexts, but omits `PromptBindings` values. Replacing a prompt input therefore changes the execution fingerprint without identifying the changed node.

**Reproduced:** replace `greet(name: input;)` with a binding to the literal `"different"`. `ExecutionFingerprintEqual` becomes false, but both the inference and return node are classified `Unchanged`; no changed root explains this binding-only edit.

This is an explanation defect. The comparer is explicitly not authorization for runtime reuse, and this review does not claim it bypasses execution checks. It still undermines the proposed human approval/revision experience.

**Recommended fix:** compare canonical, normalized prompt-binding values as dependencies. Also consider attributing changed prompt definitions to affected inference nodes, rather than leaving users to interpret only a root-level change.

**Acceptance tests:** literal changes, input/node projections, source-node changes, and equivalent reordered bindings. Check the node-level explanation as well as the fingerprint.

### R34 — P2: Media generation ignores the plan-declared timeout

**Evidence:** [BaizeGenerationInferenceExecutor.cs](../src/Penghou.Fuwen.Baize/BaizeGenerationInferenceExecutor.cs), lines 267 and 452–458; [authoring contract](fuwen-authoring.md), lines 14–17.

Generation execution uses `binding.Policy.Timeout` but never consults `request.Limits`. Consequently, the source-level timeout contract does not apply consistently across inference adapters.

**Reproduced:** a cooperative fake generation provider completed after approximately 1.61 seconds. The request declared a one-second timeout and the host allowed ten seconds. The adapter returned success.

**Recommended fix:** use the stricter of the supported host and plan deadlines. Define the covered interval precisely: submission, polling, and any publication phase. Preserve an unknown/possibly committed outcome when a provider may continue after local cancellation; do not imply cancellation guarantees remote rollback. Reject unsupported limit types explicitly instead of silently ignoring them.

**Acceptance tests:** plan tighter than host, host tighter than plan, caller cancellation, submission and polling timeout, and publication boundaries. Keep timeout failures non-retryable under the declared contract.

### R35 — P2: Workflow-owned prompt requests silently omit supplied context

**Evidence:** [BaizeInferenceExecutor.cs](../src/Penghou.Fuwen.Baize/BaizeInferenceExecutor.cs), lines 539–565; [ADR 0005](decisions/0005-inference-contracts-are-self-describing.md).

The template branch maps `ContextInputs` into its context payload. The workflow-owned-prompt branch maps only rendered messages. It neither sends the separate context inputs nor rejects their presence. A workflow can successfully gather and account for context without making that information available to the model, unless the author separately repeats it through prompt parameters.

**Reproduced:** a prompt request containing one typed context input with a unique fact succeeded, but the captured model request contained only `Hello Alice.` The context fact was absent.

ADR 0005 intentionally distinguishes typed context dependencies from interpolated text. The answer is not to indiscriminately append raw artifacts or hidden host instructions to every prompt.

**Recommended fix:** define an explicit, bounded, host-controlled context delivery contract for workflow-owned prompts, with its mapping policy represented in identity/evidence. Alternatively, reject unmapped context and document an explicit parameter-based mechanism. Distinguish evidence-only dependencies from model-consumed context if both are intended.

**Acceptance tests:** unique context facts reaching the intended model input, snapshot identity, truncation/redaction policy, no implicit artifact dereferencing, and identical behavior across sequential, repeat, and fan-out inference paths.

### R36 — P2: The source compiler hides catalogue discovery behind its cache

**Status:** resolved in the working tree as of 2026-09-21. The
binding cache preserves optional discovery and immutable snapshot identity
independently, emits exact pins, and does not add discovery to exact-only
catalogues. Tests cover discovery-capable, exact-only, in-memory, cache-hit,
failure, cancellation, and lookup-accounting paths. A custom catalogue that
omits failure details now receives a stable resolver diagnostic.

**Evidence:** [FuwenSource.cs](../src/Penghou.Fuwen.Compiler/FuwenSource.cs), lines 338, 462–482, and 1419.

Descriptor shorthand resolution checks `ITrustedCatalogueDiscovery`. `CompileAsync` wraps the supplied catalogue in `CachingCatalogue`, which implements only `ITrustedCatalogue`. The abstraction introduced for historical R17 is therefore unavailable at the parser's actual call site.

**Reproduced:** `InMemoryTrustedCatalogue.TryGetDescriptor` resolved `profile@1`; compiling the same unpinned name through `FuwenSourceCompiler` failed with `FWN-BINDING-004` requiring an exact trusted identity. The fully pinned version succeeded.

**Recommended fix:** preserve optional discovery capabilities through the decorator, while ensuring emitted plans still contain exact pins. Review other optional catalogue capabilities for the same wrapper problem without inventing capabilities the wrapped catalogue does not possess.

**Acceptance tests:** discovery-capable and exact-resolution-only custom catalogues, the in-memory catalogue, cache hits, and unchanged lookup-budget accounting. This is an integration regression related to R17, not a recommendation to reintroduce a concrete catalogue cast.

### R37 — P2: The machine-readable grammar discards newer inference syntax

**Status:** grammar defect resolved in the working tree as of 2026-09-20. The
duplicate production is removed and current inference, repeat, checkpoint,
wait, and fan-out shapes are represented. A recursive duplicate-key and
production-shape test guards the contract. README reconciliation and the full
compiled documentation corpus remain tracked by M2.8–M2.10.

**Evidence:** [fuwen-grammar.json](fuwen-grammar.json), lines 18, 25–30, and its fan-out semantic rule.

The `productions` object contains two `inferenceNode` keys. The second is an older definition without workflow-owned prompts, tools, or limits. Reading the file with PowerShell `ConvertFrom-Json` selected that second definition. Consumers that reject duplicate names may reject the document instead.

Separately, `node` omits repeat/checkpoint/wait, and the grammar still restricts fan-out bodies to activities and conditionals. Both inference productions also present the context clause as mandatory, although the current README's context-free example is accepted. The [authoring contract](fuwen-authoring.md) repeats the obsolete fan-out restriction.

This is a functional usability issue for a project intended to support machine-authored source: the compiler and its authoring reference disagree about the language.

**Recommended fix:** remove duplicate productions, update the feature coverage, and make documentation conformance a release gate. Ideally generate the authoring reference and feature inventory from shared metadata; otherwise maintain an explicit tested syntax corpus.

**Acceptance tests:** recursive duplicate-JSON-key detection, compile every documented example, and at least one reference fixture per supported node kind and inference form.

### R38 — P2: Publication does not enforce the checked-in release gates

**Evidence:** [publish.yml](../.github/workflows/publish.yml), lines 4–7, 13–34; [ci.yml](../.github/workflows/ci.yml), lines 4–5 and 31–38; [release checklist](release-checklist.md).

The publication workflow runs on tags or manual dispatch, packs, and pushes. It does not run the test/format/golden-vector gates or depend on a successful validation job for that exact commit. On a tag it replaces the version read from the project with the tag text, instead of checking the checklist's required equality.

Thus the repository workflow permits publication without proving its own checklist was satisfied. An independently configured GitHub restriction may mitigate this, but was not inspected here. No faulty release or exploit was demonstrated.

**Recommended fix:** require a reusable validation job for the exact release commit, reject tag/project version disagreement, and publish the validated artifacts. Define a deliberate policy for manual dispatch instead of allowing it to bypass these checks.

**Acceptance tests:** an invalid version or failing test blocks publication; a successful release uses the tested commit and package set. Verify this without pushing real packages during tests.

## Product and design opportunities

### 1. Make tool usefulness an explicit contract, not an implied capability

The stock Baize adapter exposes tool definitions, but does not implement a general tool execution/result-feedback loop. `BaizeToolBinding` contains a descriptor and `LlmTool`, not an execution handler. Structured-output mode rejects any returned tool call; `ToolCall` mode extracts one expected call's argument JSON as the result. It does not execute that tool.

**Observed:** a fake model requesting the declared `search` tool received `ToolMappingFailure: The structured response contained an unexpected tool call.` See [BaizeInferenceExecutor.cs](../src/Penghou.Fuwen.Baize/BaizeInferenceExecutor.cs), lines 109–126 and 699–717.

This is a product gap/contract clarification, not proof that no host can supply a richer client. Distinguish three supported experiences: structured response via a synthetic output tool, model-proposed actions returned to the host, and actual bounded tool execution. Document which adapter provides each.

If adding the third, use an optional host execution port with exact allowlists, typed arguments/results, per-call durable evidence, stable operation identities, finite rounds, and aggregate limits. Start with read tools. Idempotency of one write operation does not make a newly generated sequence of tool calls safe to replay; close that evidence/recovery contract before presenting write tools as a complete experience.

**Success criterion:** a runnable example performs one permitted lookup, feeds the result back to the model, produces typed output, and recovers without repeating a completed side effect. Every tool invocation is explainable from durable evidence.

### 2. Ship one excellent first-run experience

Historical R20–R23 remain high-value work. The README shows attractive source, but the path to an admitted, executable host is distributed across many APIs and test fixtures. There is no `samples/` directory in this checkout.

Create a small checked-in reference host that works without credentials or sibling repositories:

1. Restore public packages and run a deterministic fake-provider workflow.
2. Inspect source, exact descriptor locks, diagnostics, and the compiled plan.
3. Run, deliberately fail one step, resume, and show retained evidence.
4. Change one prompt binding and explain the revision accurately.
5. Optionally replace the fake provider with a documented real binding.

Use a useful bounded task, such as turning document artifacts into a reviewed research summary, rather than only greeting a name. Keep a tiny greeting example as the ten-line introduction. The non-code example would test the portability claim independently of Guyabano's code-generation needs.

A thin optional host-builder/DI package can follow the proven sample. It should validate missing ports and policies up front, retain low-level APIs, and never hide an allow-all policy or implicit credentials.

**Target:** a developer unfamiliar with the ecosystem reaches a successful local run and a visible recovery in under 15 minutes. Measure this with actual first-time users; it is a proposed target, not an observed result.

### 3. Treat the compiler as an interactive authoring product

Provide a small CLI and reusable diagnostic renderer before a large editor extension. Proposed commands such as `fuwen check`, `format`, `explain`, and `diff` should share the library contracts and offer human-readable and structured JSON output.

Diagnostics should show source excerpts, a precise span, expected/actual types, and a bounded correction hint. Preserve existing stable diagnostic codes for automated repair. Include examples for missing descriptors, out-of-scope references, wrong tool effects, and unsupported adapter features.

Use friendly descriptor aliases plus a reviewed lockfile/catalogue manifest: resolve aliases to exact identities before admission, show lock changes in review, and never silently resolve `latest` during execution. Fix R36 before building that experience on discovery.

For LLM authors, ship a versioned authoring pack containing tested examples, the actual catalogue vocabulary, limits, diagnostic meanings, and common repairs. Do not let it depend on a stale handwritten grammar.

**Success criterion:** an author can repair a type or capability error from the diagnostic alone, and a generated workflow never needs guessed hashes or hidden host prompt knowledge.

### 4. Make runtime support discoverable before a run starts

Compilation/admission and adapter support are different questions. Registered aliases currently expose this separation badly; media generation explicitly rejects workflow-owned prompts as well.

Add host-side execution preflight against a versioned adapter feature manifest. Report unsupported prompt forms, context mapping, tool mode, output modality, missing bindings, and limit enforcement before registration or paid work. Keep this separate from the core language's validity and the authority granted by admission.

Exact prompt-digest binding in `BaizeInferenceExecutor` is a useful control, but every newly authored prompt needs a matching host binding. Supply an explicit reviewed-plan-to-binding setup path so workflow-owned prompts do not recreate hidden host configuration through ceremony. Do not replace exact matching with a permissive fallback.

### 5. Turn evidence into an operator-facing explanation

Fuwen already has the ingredients for an unusually useful workflow inspector. Start with a compact text/JSON report, not a new dashboard framework:

- what will run, with which tools, context, and effective limits;
- why admission or preflight failed;
- which node failed and whether it may have committed an external effect;
- actual versus estimated versus unknown usage/cost;
- why a revision changed a node;
- why prior evidence was reused or rejected.

Keep provenance useful without logging secrets, raw sensitive context, or unrestricted provider output by default. Separate safe summaries from opt-in, access-controlled payload inspection. Use existing invocation identities for correlation rather than creating a second identity scheme.

Before advertising seamless forks, add explicit same-fingerprint and changed-fingerprint fork scenarios. The existing R28 work should not be treated as proof of every same-plan/new-run reuse case; independently verify the retained runtime-path checks.

### 6. Close cross-feature gaps systematically

The recurring pattern in historical and new findings is a field or feature handled in one layer but omitted in another. More isolated parser tests will not resolve that pattern.

Maintain a small compatibility matrix across prompt form, inference adapter, region (sequential/repeat/fan-out), tools, context, limits, and restart. Use pairwise coverage plus targeted full-path cases for risky combinations. Each language feature should have evidence for parse, validate, normalize, fingerprint, snapshot, compare, request mapping, and replay—not merely compilation.

Refactor the large compiler/interpreter internally around typed binding evaluation, request construction, region execution, and evidence verification. Preserve public contracts and golden vectors first. A shared internal node traversal/feature inventory could reduce forgotten fields across comparison, snapshotting, accounting, and validation. Avoid turning this into a second public plugin framework.

Provide an execution-port conformance test kit for external adapters, including adversarial provider responses, unsupported capabilities, malformed evidence, cancellation, and unknown usage.

### 7. Distinguish local limits from a workflow budget

Per-attempt token/time limits and compile-time resource bounds do not by themselves express a workflow-wide cost ceiling. Repeats, fan-out, fallbacks, repair, and tools can multiply work.

Define a host-owned run budget with explicit accounting/reservations across concurrent branches, retries, and resume. Keep enforcement with the host/runtime rather than adding scheduling responsibilities to the language. Separate compiler budget, provider output limit, deadline, token allowance, monetary estimate, and committed spend; these are not interchangeable.

Specify what happens when provider usage is unknown, cancellation cannot stop remote work, or a run resumes against a changed pricing policy. Conservative failure and honest evidence are more useful than a misleading exact total.

### 8. Make documentation a reliable product surface

Besides R37, reconcile these visible contradictions:

- [README](../README.md), lines 104–105, says only read-only tools are admitted; preview.10 and the authoring contract also admit constrained writes.
- [CHANGELOG](../CHANGELOG.md) stops at preview.2 while the project version is preview.10.
- The [threat model](threat-model.md) still promises a complete model before the first public preview. Update its scope, concrete controls, residual risks, and host responsibilities without implying an audit has occurred.
- Historical R24 remains marked open even though `ObjectLiteralMatches` now handles named object schemas in [WorkflowCompiler.cs](../src/Penghou.Fuwen.Compiler/WorkflowCompiler.cs), lines 1251–1273. Reconcile its status against regression coverage instead of repeating the old defect as current.

Separate the learning path into workflow authors, host integrators, and adapter implementers. Keep historical migration notes clearly dated. Publish a compact capability table stating supported, unsupported, and experimental combinations for each package/version.

## Recommended delivery sequence

| Milestone | Work | Exit evidence |
| --- | --- | --- |
| Trust the current contract | R31–R38; turn the isolated probes into regression tests; document tool execution scope | Model-visible behavior matches the admitted plan; aliases work or fail in preflight; accurate diffs; no silently ignored limits/context; publication gates enforced |
| Make the first run excellent | Runnable credential-free host, diagnostic renderer, corrected authoring pack, thin setup helpers | A new developer completes the run/fail/resume/edit walkthrough without internal assistance or sibling checkouts |
| Make it independently useful | One bounded non-code workflow and an explicitly supported tool-execution path | Typed useful output, per-call evidence, recovery, bounded resource use, and reproducible consumer tests |
| Make safe evolution visible | Plan inspector, revision explanations, reuse reasons, lockfile changes | A user can correctly predict what a proposed edit will rerun and why |

Do not start by adding more node kinds, a broad graphical editor, marketplace infrastructure, or generic scripting. The existing language is already large enough to demonstrate the central value.

## Bottom line

Fuwen does not need a new identity. Its strongest identity is already present: **a reviewable contract for AI work that can evolve without losing control of authority, evidence, and recovery**.

The next step toward an extraordinary project is to make that promise true at every boundary and obvious in one short, useful demonstration. Prioritize model-visible contract fidelity, a complete first-run experience, and trustworthy change/recovery explanations. Those improvements reinforce one another and make the existing architecture valuable to people who did not build it.
